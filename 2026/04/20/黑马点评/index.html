登录注册流程

校验登陆状态

为了保护需要登录才能访问的接口，项目通过 Spring MVC 的拦截器（Interceptor）来实现状态校验和信息共享：

  • 拦截请求： 拦截器会拦截客户端的请求，并尝试从 HttpSession 中获取 "user" 属性。
  • 状态判断：
    • 如果没有获取到用户信息，说明未登录，直接拦截请求并返回 401 状态码。
    • 如果获取到了用户信息，说明已登录。
  • 保存至 ThreadLocal： 拦截器将获取到的 UserDTO 保存到 ThreadLocal（项目中封装为 UserHolder 工具类）中。这一步非常关键，它实现了线程隔离，使得在后续的 Controller、Service 层中，可以随时随地通过 UserHolder.getUser() 方便地获取当前登录的用户信息，而不需要把 request 对象传遍整个调用链路。
  • 放行与清理： 拦截器放行请求。在整个请求处理完毕后，必须将 ThreadLocal 中的数据清理掉，以防止内存泄漏和线程池复用导致的数据错乱。

双拦截器

拦截器一：刷新 Token 拦截器 (RefreshTokenInterceptor)

  • 拦截范围： 拦截所有路径 (/**)。
  • 核心逻辑：
    1. 尝试从请求头（Header）的 authorization 字段获取 Token。
    2. 如果没有 Token，直接放行（不拦截，交由下一个拦截器处理）。
    3. 如果有 Token，拼接 Key 去 Redis 里查询对应的 Hash 数据。
    4. 如果 Redis 里有数据，将其转回 UserDTO，存入 ThreadLocal (UserHolder)。
    5. 最重要的一步：刷新 Redis 中这个 Token 的有效期（重置为 30 分钟）。
    6. 放行。

拦截器二：登录拦截器 (LoginInterceptor)

  • 拦截范围： 只拦截需要登录的路径（比如下单、查看个人中心等）。
  • 核心逻辑：
    1. 因为它排在“拦截器一”后面，所以它不需要再去查 Redis 了。
    2. 它只做一件事：判断当前线程的 ThreadLocal (UserHolder) 中有没有 UserDTO。
    3. 如果没有，说明用户没登录（或者 Token 已经过期），拦截请求，返回 401 状态码。
    4. 如果有，说明已登录，直接放行。
